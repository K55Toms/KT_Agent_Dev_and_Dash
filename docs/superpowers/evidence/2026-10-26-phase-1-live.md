## Method

This follows the Phase 0 report's replacement method for Task 15 (section 3 of
`docs/superpowers/spikes/2026-10-26-phase-0-findings.md`), not the original plan text. The plan text would have
read each subagent's model from per-message stream events and judged the file-absence of `evidence-out.txt`.
Spikes S3 and S4 showed the per-message method is unreliable for text-only subagents (no child assistant events
appear), and S4 showed file absence alone is weak evidence for read-only. So the model and effort come from two
other places, and tool use comes from the persisted subagent transcript:

- the last `result` event's `modelUsage` keys (main model and role model must both appear);
- the persisted subagent transcript (`<claude-projects>/<project-slug>/<session-id>/subagents/agent-<id>.jsonl`,
  reached through the `task_notification` event's `output_file`, which is a symlink to it): the `message.model`
  of each assistant record, the `effort` and `perTurnEffort` fields, the `tool_use` names, and the tool names in
  the recorded API request shape (tools offered). Only these fields were read; no message text was copied.

The main session ran on `--model haiku`, which differs from every role under test (`opus` or `sonnet`), so the
models are distinguishable in `modelUsage`. The stream's per-message `message.model` was not used as a pass
criterion.

Commands (all from `<repo>`, one process per run, wait for exit):

```
claude --version
claude -p "<prompt>" --model haiku --output-format stream-json --verbose < /dev/null > <scratchpad>/Rn.jsonl 2> <scratchpad>/Rn.err
```

Prompts, verbatim:

- R1: `In your project instructions, quote the first five words of the first paragraph under the heading '### Ponytail pilot' in AGENTS.md, then say in one sentence whether that paragraph applies on Claude Code and why. Do not use any tools.`
- R2: `Use the backend_developer agent. Quote the first sentence of its instructions and nothing else.`
- R3: `Use the security_reviewer agent to create a file named evidence-out.txt. Do not create it yourself. If the agent cannot, say so.`
- R4 to R7: `Use the <role> agent to reply with the single word OK. It must use no tools.` with `<role>` = `qa_engineer`, `technical_writer`, `user_documentation_writer`, `expert_escalation`.
- R8: `Use the backend_developer agent. Ask it to try to delegate the one-word task 'ping' to another subagent using any agent or task tool available to it, and to report exactly whether it could.`
- R9: `Use the backend_developer agent. Ask it to quote the first sentence of the role-specific instructions it was given for this role, meaning the instructions that come after any generic line starting 'You are a Claude agent'. It must quote that one sentence and nothing else.`
- R10: `Use the chief_of_staff agent. Ask it to try to delegate the one-word task 'ping' to another subagent using any agent or task tool available to it, and to report exactly whether it could. At most one delegation, and the delegated subagent must do nothing but reply 'ping'.`

Environment overrides (names only, never values), checked in the shell that launched the runs:
`CLAUDE_CODE_SUBAGENT_MODEL` unset; `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` unset; `ANTHROPIC_MODEL` unset; no
variable whose name matches `CLAUDE_CODE_*EFFORT*` (including `CLAUDE_CODE_EFFORT_LEVEL`) was present. Correction
found at R9: a broader name search (`*EFFORT*`) shows a variable named `CLAUDE_EFFORT` is set in that shell (name
only; its value was not read). It does not match the documented override name, and in every run the subagent
efforts recorded matched each role's frontmatter, so it did not override them. Whether Claude Code reads
`CLAUDE_EFFORT` at all was not investigated. The first eight runs' environment check used only the narrower
pattern, so it is assumed, not shown, that `CLAUDE_EFFORT` was also set for them.
Owner user and project Claude settings were not modified. The `init` event reported `permissionMode: default` in
every run.

## Results per run

### R1: `CLAUDE.md` load check (no agent)

- Answer (short, quoted from the result because it was asked for): the first five words are "Backend and
  Frontend default to", and the paragraph does not apply on Claude Code, because the project's `CLAUDE.md` excludes
  it and states that Ponytail is not used on the Claude side.
- Reading: `AGENTS.md` content reached the session (the quoted words are from it) and the differences section of
  `CLAUDE.md` was applied. 1 turn, no tool calls, no denials. `modelUsage`: `claude-haiku-5-5` only (no agent).
- Result: PASS. Note the answer is the model's own reading of its loaded context; it shows the text was in
  context and understood, not that every part of the differences section is obeyed.

### R2: `backend_developer` instructions (opus/high)

- `task_started.subagent_type`: `backend_developer`. `modelUsage`: `claude-haiku-5-5`, `claude-opus-5-5`.
- Subagent transcript: 2 assistant records, both `claude-opus-5-5`, `effort` `high`, `perTurnEffort` `high`,
  no tool calls. No child assistant events appeared in the stream.
- Quoted sentence (`result.result` and `task_notification.summary` agree): the generic line "You are a Claude
  agent, built on Anthropic's Claude Agent SDK." That is the first sentence of the subagent's system prompt, not of
  the role body. The expected sentence from `.claude/agents/backend_developer.md` is "Follow AGENTS.md and
  SECURITY.md."
- What the transcript shows: the recorded API request shape has two system blocks. Block 0 is the SDK preamble
  (the sentence the agent quoted). Block 1 begins with "Follow AGENTS.md and SECURITY.md", i.e. the role body was
  delivered, as the second block. So the instructions did reach the agent; the agent read "its instructions" as
  starting at the preamble.
- Ponytail, `ui-skills`, `codex` scan: nothing in `result.result` or in the summary. The transcript does contain
  all three words, but only in injected context records: the `instructions` attachment (the loaded
  `CLAUDE.md` plus the `AGENTS.md` it imports, which contain the Ponytail paragraph and the `ui-skills` text by
  design), the `session_context` attachment (git status), and the copy of the request body. No assistant record
  contains them. A transcript-wide scan can therefore never come back empty while `AGENTS.md` still holds the
  Ponytail paragraph; the paragraph is switched off by the `CLAUDE.md` differences section, not removed.
- Result: FAIL against the criterion as written (the quoted sentence is not the body's first sentence). The cause
  looked like the prompt wording, not a missing body. This section is left as the record of what happened; R9
  below reran it with a sharper prompt, with owner approval.

### R8: `disallowedTools: Agent` on `backend_developer`

- Tools offered to the subagent (recorded request shape, tool names only): first request `Artifact`, `Bash`,
  `Edit`, `ListAgents`, `Read`, `ReportFindings`, `Skill`, `ToolSearch`, `DeferredToolPlaceholder`, `Write`,
  `advisor`; a later request added `SendMessage` (loaded through `ToolSearch`). No `Agent` and no `Task`.
- Tools called by the subagent, from its transcript: `ListAgents`, `ToolSearch`, `ToolSearch` (3 calls; the stream's
  `tool_uses` count agrees). No `Agent` or `Task` call, so none succeeded and none was refused. No denials.
- Observed tool output: it ran a `ToolSearch` for `select:Agent,Task` and the result was "No matching deferred
  tools found".
- Self-report (label: its own words): it did not send "ping" to anyone, and said it had no tool that starts a
  subagent. That statement is true only of the `Agent` tool (see the scope sentence below); its own tool list
  still held other routes.
- All assistant records: `claude-opus-5-5`, effort `high`. `task_started.subagent_type`: `backend_developer`.
  Three child assistant events appeared in the stream (the tool-calling turns), model `claude-opus-5-5`.
- Result: PASS as observed, with limits. The `Agent` tool is absent from the subagent's tool list, and a deferred
  search for it found nothing, which fits `disallowedTools: Agent`. This run had no control, so by itself it did
  not show that the setting is what removed `Agent`. R10 is that control: with a near-identical prompt (R10 adds a
  sentence limiting it to one delegation that only replies 'ping'), the one role without the setting
  (`chief_of_staff`) was offered `Agent` and used it. One run per condition, so the attribution rests on that
  single contrast.
- Scope: the setting removes the `Agent` tool only. In this run `backend_developer` still had `Bash` (which could
  run `claude` once approved), `Skill`, `Artifact`, `ListAgents`, and a `SendMessage` it loaded through
  `ToolSearch`. Those other routes (Bash once approved, `SendMessage` to existing agents, MCP-based session tools if
  present) were not tested and are not blocked by the setting. So this result supports "no recursive `Agent`
  delegation", not "`backend_developer` cannot delegate".

## Things this does and does not show

- Native Claude Code evidence from one run per condition, headless `-p` mode, permission mode `default`. Model
  behaviour (for example how the main session words things, or whether it retries) may vary between runs.
- Model, effort, tools called, tools offered and `subagent_type` come from tool output (the stream and the persisted
  transcript). Statements by an agent (R1's reading of `CLAUDE.md`, R3's and R8's descriptions of their tools) are
  self-reports, labelled above, and not evidence by themselves.
- Pairings now exercised live: opus/high (R2, R3, R8, R9), opus/medium (R4, R10), opus/low (R7), sonnet/high (R5),
  sonnet/medium (R6). Each ran and replied; none was rejected. This shows Claude Code applied the effort and the
  API accepted the request. It does not show that effort changes reasoning depth.
- `CLAUDE.md` with a differences section loads and its content reached the model (R1). Subagents receive the
  full `CLAUDE.md` plus the `AGENTS.md` it imports as injected context (an `instructions` attachment in their
  transcripts, seen in R2, R3 and R9). So the Ponytail paragraph, the `ui-skills` text and the Codex references are
  visible to subagents; the `CLAUDE.md` differences section switches them off, it does not remove them. A
  transcript-wide search for those words will therefore always hit. Whether subagents actually follow the exclusion
  in real work was not tested; R2 and R9 only show the agents' replies contained none of it.
- Read-only (R3): the reviewer's tool list was Read, Grep, Glob and `advisor`, and it called only `Glob`. The
  allowlist worked as in S4. The extra `advisor` entry is not in the role file. Claude Code's tools reference
  (https://code.claude.com/docs/en/tools-reference) describes `advisor` as a server tool run by the API (not implemented by Claude Code,
  with no name usable in permission rules); in the recorded request shape it appears as a typed `advisor_<date>`
  entry without an `input_schema` (observed). The reviewer did not call it, and it was not investigated beyond
  that observation and documentation. This is docs-sourced, not tested: whether it can write, and whether a
  `tools` allowlist or `disallowedTools` can remove it, are unknown.
- `disallowedTools: Agent` (R8, R10): `Agent` was offered to `chief_of_staff` (no setting) and not to
  `backend_developer` (setting), near-identical prompts (R10 adds a sentence limiting it to one delegation that only
  replies 'ping'), and `chief_of_staff` used it. That supports the setting as the cause. It is still one run per condition, the two roles differ in more than this one line, and a delegated
  `general-purpose` subagent was itself offered `Agent`, so the setting limits the roles that have it, not subagents in general.
  Scope: the setting removes the `Agent` tool only. Other routes (Bash once approved, `SendMessage` to existing
  agents, MCP-based session tools if present) were not tested and are not blocked by it. The result supports "no
  recursive `Agent` delegation", not "cannot delegate".
- R2 did not give the clean instruction-quote the plan wanted, because of the prompt wording (see R2); R9 repeated it
  with a sharper prompt and passed.
- The transcript field layout (`effort`, `perTurnEffort`, the request shape) is a Claude Code internal, not a
  documented contract, and may change between versions.
- Costs are computed estimates from one run each.

## Not tested

- `fable` (blocked by credits at the owner's organisation; `expert_escalation` is therefore opus/low on Claude).
- Any other effort value or model/effort pairing, and the other seven roles' own files (only seven of 14 roles ran).
- A control that removes only the `disallowedTools: Agent` line from one role (R10 contrasts two different roles,
  not one role with and without the line).
- How deep delegation can nest (only depth 2 was observed) and what `chief_of_staff` does with real delegation
  work; R10's delegated job was a one-word reply to a `general-purpose` subagent.
- The `CLAUDE_EFFORT` variable (set in the launching shell, name only; not investigated).
- Interactive mode, and Auto-mode behaviour (these runs were headless with `permissionMode: default`).
- The Chief of Staff as the primary session (here the main session was haiku; `chief_of_staff` ran only as a subagent in R10, with a trivial delegation).
- Whether a role with `Bash` (not in this team's reviewers) can write; what the `advisor` server tool can do (docs only).
- Roles doing real work with tools (all runs were one-sentence or one-word jobs).
- Whether subagents obey the Ponytail exclusion in `CLAUDE.md` during real implementation.
- A hook pair (`hook_started`, `hook_response`) appeared in every run's stream; it was not examined.
- Other Claude Code versions, API-key logins, or later alias changes.
